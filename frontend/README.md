# Paradox Protocol — Judge Dashboard (18 September)

## 1. Frontend purpose

Judge-facing demonstration and evaluation interface for **Adaptive Variable-Resolution
2.5D LiDAR Mapping**. It explains, for one replayed frame at a time:

```
What the system receives (replayed LiDAR)
        ↓
What the system calculates (importance, resolution, 2.5D map — all from backend)
        ↓
Where importance is high/low (Importance view)
        ↓
What resolution is assigned (Resolution view)
        ↓
What the final adaptive 2.5D map looks like (Adaptive Map view)
        ↓
What performance was measured (Live Metrics + stored Benchmark comparison)
```

The frontend **visualizes backend outputs only**. It contains no ML logic, no tuning
controls, and never invents metrics: unavailable values render as `Unavailable` or an
explicit empty/error state.

## 2. Technology

React 19 + TypeScript + Vite (production build served locally via `vite preview`).
No chart/map framework — lightweight canvas rendering of the backend-supplied cells.
Tests: Vitest + Testing Library. E2E: puppeteer-core against system Chrome.

## 3. Installation

```bash
cd frontend
npm install
```

Regenerate the stored benchmark asset after any validated change to
`results/benchmark/`:

```bash
npm run benchmark:asset   # == python ./scripts/generate-benchmark-asset.py
```

## 4. How to start

```bash
npm run dev      # local dev server  (http://127.0.0.1:5173)
npm run build    # production bundle (tsc + vite build)
npm run preview  # serve the bundle (http://127.0.0.1:5173)
npm test         # vitest suite (19 tests)
```

Full demo needs **two terminals** — see `simulation_handoff/START_DEMO.md`.

## 5. Backend URL

`VITE_API_BASE_URL` (see `.env.example`). Default when unset: `http://127.0.0.1:8000`.
Local loopback only — never point the judge demo at a public endpoint.

## 6. Required backend endpoints

| Call | Endpoint |
|---|---|
| health | `GET /health` |
| config metadata | `GET /config` |
| frame list | `GET /frames` |
| load | `POST /replay/load` |
| run (frozen pipeline) | `POST /replay/run` |
| stored result | `GET /results/{frame_id}` |
| measured metrics | `GET /metrics/{frame_id}` |
| demo state | `GET /demo/status` |

All HTTP lives in `src/api/client.ts`. Components never call `fetch()` directly.

## 7. Demo workflow

1. Start backend (`uvicorn backend.app:app --host 127.0.0.1 --port 8000`), confirm
   `Backend: Connected / Model: Loaded` in the header.
2. Select a frame in Panel A (list comes from `GET /frames`).
3. Press **Run** (`POST /replay/run` on the frozen pipeline).
4. Read Panels B→C→D→E→F, then the stored Benchmark comparison and the
   "How it works" explanation.

## 8. Visualization data source

Every visualization consumes the single `currentResult: PipelineResult` in
`src/hooks/useReplay.ts` (one frame, one result — metadata/map/metrics cannot go
stale relative to each other). Canvas helpers in `src/utils/visualization.ts` are
pure display scales (backend value → color/size); they compute no importance or
resolution. Resolution tiers (`0.05/0.10/0.20/0.50 m`) are descriptive labels for the
frozen config, confirmed at runtime via `GET /config`.

## 9. Benchmark data source

`public/benchmark.json` — generated by `scripts/generate-benchmark-asset.py` from:

```
results/benchmark/benchmark_summary.csv
results/benchmark/benchmark_results.csv
results/benchmark/resolution_distribution.csv
results/benchmark/benchmark_config.json
```

> Benchmark values shown here are loaded from the validated benchmark results and
> are not recalculated by the frontend.

The panel shows the three stored methods (Proposed Adaptive, Uniform 5 cm,
Distance-based Adaptive) tagged **Stored benchmark result**, plus the live frame
tagged **Current replay result** — never mixed.

## 10. Known limitations

- Map views render at most 4000 cells (frontend visualization subset); the measured
  counts always reflect the full backend result.
- `vite preview` serves the static benchmark asset; live backend must still run for
  all replay/metric data.
- Semantic labels are annotation-derived evaluation references (`annotation`,
  `lidarseg_annotation`, `object_annotation`, `fallback`, `unknown`) — never shown
  as AI/model predictions unless the backend reports `model_prediction`.
- No auto-run on startup: the judge presses Run explicitly, keeping the demo
  predictable.
